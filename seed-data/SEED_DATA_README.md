# Seed Data - Design, Operation and Decisions

How the development dataset is built, how to (re)create it, and every decision taken because of what the **current** source code does. The record-level documents ([credentials](credentials.md), [USERS_AND_MANAGERS](USERS_AND_MANAGERS.md), [RETAILERS](RETAILERS.md), [FLEET](FLEET.md), [CUSTOMERS](CUSTOMERS.md), [CATEGORIES](CATEGORIES.md), [PRODUCTS](PRODUCTS.md), [PRODUCTS_AND_TAX](PRODUCTS_AND_TAX.md), [CARTS_AND_WISHLISTS](CARTS_AND_WISHLISTS.md), [ORDERS](ORDERS.md), [LOGISTICS](LOGISTICS.md), [REVIEWS](REVIEWS.md), [VERIFICATION](VERIFICATION.md), [FINANCE](FINANCE.md), [SUPPORT](SUPPORT.md), [NOTIFICATIONS_AND_AUDIT](NOTIFICATIONS_AND_AUDIT.md)) are generated from the seeded database itself.

## 1. What the project actually is (analysis result)

* **Six services on one database.** S1 platform & territory (identity, states / cities / zones, operations and location managers), S2 partner verification (retailers, fleet owners, verification queues and documents), S3 commerce & customer (customers, addresses, categories, products, cart, wishlist, reviews), S4 order & logistics (orders, items, trips, logistics bookings), S5 fleet (drivers, vehicles, assignments, expenses), S6 finance & support (payments, invoices, settlements, refunds, tax, tickets, clusters, notifications, audit log). All six point at the same PostgreSQL database; each service's Hibernate `ddl-auto=update` creates its own tables (39 in total); there are **no foreign keys between services** - references are scalar ids.
* **Ids.** S1/S2/S5/S6 entities use random UUIDs generated by Hibernate; S3 products / categories, S4 orders / order items and S6 notifications use database identity `Long`s. The seed follows the same mechanisms: it never assigns an id - it inserts rows without one where the database generates it, uses `UUID.randomUUID()` (what Hibernate does) elsewhere, and finds the other services' rows by **business key** (email, business name, SKU, registration number, order number). The *previous* seed relied on a table of fixed literal UUIDs and on identity values being "deterministic"; both are gone.
* **Passwords.** S1's `PasswordEncoder` is `PasswordEncoderFactories.createDelegatingPasswordEncoder()` (BCrypt). The old seed stored `{noop}` plaintext; the new one calls the same encoder, so the stored value is a `{bcrypt}` hash. The single development password is `Lbos@2026!` (it satisfies the password policy: 8-72 characters, upper, lower, digit, special). **The login rejects a password older than 90 days** (`AuthController.MAX_PASSWORD_AGE_DAYS`, HTTP 423 "Password has expired") by the REAL clock, so `password_changed_on` is dated relative to the moment the account is seeded (not to the fixed dataset moment), and every start of S1 sets it to "yesterday" again for a seed account that still has the seed password and whose password is older than 30 days. An account whose password somebody changed is never touched, so a dev database keeps working however long it lives.
* **Roles that can log in** need their profile in the right state (`LoginEligibilityService` and the partner gates): retailers `VERIFIED`, fleet owners `VERIFIED` + `ACTIVE`, drivers `ACTIVE`, managers with an `ACTIVE` assignment - all seeded that way, with the APPROVED verification trail that produces those states.
* **Orders are one per retailer.** The frontend's checkout creates one `RETAIL` order per retailer of the cart (`ORD-<epoch ms>-<n>`), adds the items (S4 fetches the product from S3, snapshots SKU / name / price / weight and deducts stock), submits it, then S6 creates and captures the payment. The retailer accepts (`FINDING_DELIVERY_PARTNER`), a fleet owner creates the trip (`VEHICLE_ASSIGNED`), the driver confirms pickup (`IN_TRANSIT`) and completes it (`DELIVERED`, escrow released, settlements created). The seed replays exactly these end states and intermediate histories.
* **Tax is per product category and state.** `S6.tax_configuration.product_category_id` points at the S3 category; checkout sends the category of every line and S6 taxes each line with the active rule of that category in the delivery city's state (no default rate). The seed creates the rules (24 active + 1 historic) and S4 reads them to compute the tax the orders were charged.
* **What the entities do *not* have.** The current model has no product brand / MRP / cost price / unit / dimensions / image URL, no customer name or gender on `customer_profile` (names and phones live in `user_account`), no driver name / date of birth / gender / address (name and phone are on the account, position and licence on the driver), no vehicle insurance or registration date columns (insurance is a *verification document*), no `OrderHistory` table (order history is the `status_history_json` column plus `trip_status_history`), and no separate inventory table (stock is `products.stock_quantity`). Nothing was invented to fill such fields: the requirement lists ("if present") were followed against the real entities, and the data those concepts need is stored where the application keeps it. See [ENTITY_FIELD_COVERAGE.md](ENTITY_FIELD_COVERAGE.md) for every column.

## 2. The seeders

| Service | Class | Writes | Waits for |
|---|---|---|---|
| S1 | `S1-platform-territory/.../seed/DataSeeder.java` | territory, 34 accounts, managers, transfer history | - |
| S2 | `S2-partner-verification/.../seed/DataSeeder.java` | retailers, fleet owners, queues, documents (driver / vehicle queues once S5 has its rows) | S1, S5 |
| S5 | `S5-fleet-operations/.../seed/DataSeeder.java` | drivers, vehicles, assignments, expenses | S1, S2 |
| S3 | `S3-commerce-customer/.../seed/DataSeeder.java` | customers, addresses, categories, products, carts, wishlists (reviews + reward points later) | S1, S2, S4 |
| S4 | `S4-order-logistics/.../seed/DataSeeder.java` | orders, items, trips, history, bookings | S1, S2, S3, S5, S6 |
| S6 | `S6-finance-support/.../seed/DataSeeder.java` | tax rules; then payments, settlements, invoices, refunds, tickets, messages, cluster, notifications, audit | S1, S3, S4 |

`SeedSupport.java` (one identical copy per service - the services share no code) holds the helpers: the dataset moment, `await(...)` (poll for another service's row for up to 7 minutes), the synthetic PDF and the shared payment-reference rule (`TXN` + digits derived from the order number, used by S4 and S6 so they agree without sharing anything).

* **Order of start does not matter.** A seeder that needs another service's row waits for it (up to 7 minutes). Every service except S1 runs its seeder on a **background daemon thread**, so a service starts (and its tests load) without waiting for the others; a seeding failure is logged (`seed-s? failed: ...`) instead of failing the service. Rows that depend on orders (reviews, reward points, driver / vehicle verification, everything financial) are written later in the same thread, once the orders exist. Set `app.seed.enabled=false` (env `APP_SEED_ENABLED=false`) to switch a service's seeder off; S1's seeder is synchronous and always runs.
* **Idempotent.** Every row is checked by a natural key first; a restart of all six services changes nothing (verified, see [DATA_VALIDATION.md](DATA_VALIDATION.md)). A half-finished earlier run is completed, not repeated.
* **Dates.** Everything is dated relative to one fixed moment - **2026-09-20 18:00 IST** ("as of") - so history is chronological and reproducible; nothing is in the future. Live states are chosen so the application's own schedulers leave them alone: no order waits in `WAITING_FOR_RETAILER` (S4's retailer-timeout job would cancel it after 10 minutes), the only OPEN ticket is LOW priority (SLA 72 h), in-transit / planned trips are from the same afternoon. The ticket-cluster scheduler re-evaluates the incident with the real clock and resolves it once 48 hours have passed - the seeder never adds a second one.
* **JDBC vs JPA.** Rows are written with `JdbcTemplate` because the seed backdates `created_at` / `updated_at`, which the entities' `@PrePersist` callbacks would overwrite. S4's orders, order items and logistics bookings use the repositories (JSON columns).
* **Store hours.** Customers only see the products of stores that are OPEN RIGHT NOW by the real clock (S2 `getOpenRetailerIds`; S3 hides everything if no store is open), and a zone has only one or two stores - so realistic hours (e.g. 07:00-22:00) made the whole catalogue vanish at night. The five seeded stores are therefore open all day (00:00 - 23:59:59). Edit a store's opening hours on its profile to try the closed-store behaviour.
* **Deviations from what the API writes (deliberate, documented):** `orders.transaction_reference` and `payment_transaction.provider_reference` are filled (the API leaves both `null`); `status_history_json` holds the transitions (the API leaves `[]`); the S3 stock shown is the opening stock less the seeded orders (S4 deducts it exactly as `InventoryClient` does); tickets, messages and audit rows are dated in the past.

## 4. Recreate, reset, verify

```text
# start from an empty development database (DEVELOPMENT ONLY - deletes everything)
psql -h <host> -U <user> -d <dev database> -f seed-data/RESET_DEVELOPMENT_DB.sql

# start the six services in any order; each logs "S? seed: ..." lines as it finishes
# verify (part 2 of the output must be all zeros)
psql -h <host> -U <user> -d <dev database> -f seed-data/VALIDATE_SEED_DATA.sql

# regenerate the record-level documents from the running dataset
java -cp <jdbc driver jar> seed-data/tools/GenerateSeedDocs.java <jdbc-url> <user> <password> seed-data
java -cp <jdbc driver jar> seed-data/tools/Coverage.java <jdbc-url> <user> <password>     # column coverage
```

A database that was seeded by the previous version still holds the old rows (`@aroundu.local` accounts, fixed-id partners, orders `ORD-SEED-*`): run the reset script once before starting the services - the new seeders do not touch old rows. The old seed material was removed from the project (the six old `DataSeeder` classes were rewritten, `scripts/seed-all-databases.sql` was deleted, `docs/SEED_DATA_CONTRACT.md`, `credentials.md`, `DEMO_GUIDE.md` and the run guides were updated).

## 5. Limitations

* Validated end to end on **H2** and then on a **local PostgreSQL 18** (clean start, restart = idempotent, `RESET_DEVELOPMENT_DB.sql` + reseed) - see [DATA_VALIDATION.md](DATA_VALIDATION.md). `scripts/create-local-database.cmd` creates the empty role + database that the services' default settings expect (then set `DB_URL` to your server).
* The seeders write with JDBC directly into the shared database (waiting on other services' tables). That is a seeding-only shortcut - at runtime the services still talk to each other through their APIs.
* `docs/api-reference/*.md` are QA logs recorded against the previous dataset; their emails and ids no longer exist.
