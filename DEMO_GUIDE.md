# AroundU — Demo Guide

Six Spring Boot microservices (S1–S6) + Eureka + API Gateway. Every service now
self-seeds its own demo data on startup (no Flyway anywhere, no manual DB setup) and
every priority flow below has been live-verified end to end, through the Gateway, with
real JWTs.

## 1. How to start everything

No external database needed — every service runs on embedded H2, seeded automatically.

```bash
cd eureka-server && ./mvnw.cmd spring-boot:run        # wait for port 8761
cd S1-platform-territory && ./mvnw.cmd spring-boot:run  # port 8081 — start before the rest (owns identity)
cd S2-partner-verification && ./mvnw.cmd spring-boot:run # port 8082
cd S3-commerce-customer && ./mvnw.cmd spring-boot:run     # port 8083
cd S4-order-logistics && ./mvnw.cmd spring-boot:run       # port 8084
cd S5-fleet-operations && ./mvnw.cmd spring-boot:run      # port 8085
cd S6-finance-support && ./mvnw.cmd spring-boot:run       # port 8086
cd api-gateway && ./mvnw.cmd spring-boot:run              # port 8080 — start last
```

Or use `scripts\start-all.cmd` / `scripts\stop-all.cmd` from the project root.

Confirm everyone registered: `curl http://localhost:8761/eureka/apps` — look for
`LBOS-PLATFORM`, `LBOS-PARTNER`, `LBOS-COMMERCE`, `LBOS-ORDER`, `LBOS-FLEET`,
`LBOS-FINANCE`, `LBOS-GATEWAY`. All external traffic should go through the Gateway
(`http://localhost:8080`); each service's Swagger UI is also directly reachable at
`http://localhost:<port>/swagger-ui.html` for isolated testing.

## 3. Login (JWT)

```bash
curl -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@lbos.com","password":"Lbos@2026!"}'
```

Response: `{"accessToken": "...", "userAccountId": "...", "role": "SUPER_ADMIN", ...}`.
Use it on every subsequent call: `-H "Authorization: Bearer <accessToken>"`. Customers
can also self-register: `POST /api/v1/auth/register/customer`.

## 5. Exact Swagger inputs for the priority APIs

### S1 — Operations Manager (admin token required)

**`PATCH /api/v1/operations-managers/{id}/city`** — `id = 40000000-0000-0000-0000-000000000001`, body:
```json
{ "cityId": "20000000-0000-0000-0000-000000000003" }
```
→ 200, manager reassigned to Bengaluru. Retry with a bogus `cityId` → 404. Retry with a
`cityId` belonging to a deactivated city → 409.

**`GET /internal/v1/operations-managers/{id}/validate-city/{cityId}`** (Basic auth
`lbos-service` / `service123`) — try the manager's actual city → `{"valid":true,...}`;
try a different city → `{"valid":false,"reason":"...not assigned to the requested
city"}`.

### S2 — Document upload

**`POST /api/verification-documents/upload`** (multipart/form-data — Swagger renders a
real file picker):
- `verificationQueueId`: `72000000-0000-0000-0000-000000000002`
- `documentTypeName`: `PAN_CARD`
- `file`: any real PDF/JPG/PNG under 10MB

→ 201, new version created, old version flipped to `isCurrentVersion=false`. Retry with
a `.exe` file → 400. Retry with an empty file → 400. Retry with an 11MB file → 400.
Then **`POST /api/verification-queues/{queueId}/process-result`** with
`{"result":"APPROVED"}` → retailer2's `retailerStatus` flips to `VERIFIED`.

### S3 — Cart / wishlist / checkout (customer1 token)

- `POST /api/v1/cart/validate` — validates current cart contents/stock.
- `POST /api/v1/cart/items/{id}/move-to-wishlist` — moves a cart line to the wishlist.
- `POST /api/v1/customers/me/wishlist-items/membership` with a list of product ids →
  `{"1": true, "2": false, ...}`.
- `POST /api/v1/checkout/prepare` — happy path returns a checkout preview; with a
  downstream service down, returns 503 (not a raw 500).

### S5 — Vehicle & assignment (fleetowner1 or admin token)

**`POST /api/vehicles`**:
```json
{ "fleetOwnerId": "71000000-0000-0000-0000-000000000001", "registrationNumber": "TN01ZZ9999", "vehicleType": "MINI_TRUCK" }
```
→ 200. Retry with the same `registrationNumber` → 409. Retry with a bogus
`fleetOwnerId` → 400.

**`POST /api/assignments`** — use the deliberately-unassigned pair:
```json
{ "vehicleId": "a0000000-0000-0000-0000-000000000002", "driverId": "a1000000-0000-0000-0000-000000000002" }
```
→ 200. Retry the same call again → 409 (vehicle/driver already active). Try assigning
vehicle 1 (already assigned to driver 1) to a different driver → 409.

### S6 — Escrow-style payment lifecycle (admin token)

No literal "Escrow" entity exists in this codebase — the equivalent, already-existing
mechanism is `PaymentTransaction.escrowStatus` (`HELD` → `RELEASED`) plus `Settlement`
and `CustomerRefund`. Demo flow:
- `GET /api/payment-transactions` → find the order-2 payment (`escrowStatus: HELD`).
- `POST /api/payment-transactions/{id}/release-escrow` → 200, becomes `RELEASED`.
  Call it again → 409 (already released).
- `POST /api/settlements` with that payment id → creates a `PENDING` settlement.
  Call it again for the same payment → 409 (duplicate).
- `POST /api/settlements/{id}/complete` → 200, `COMPLETED`. Call again → 409.
- `GET /api/customer-refunds` → find the seeded `REQUESTED` refund for order 2 →
  `POST /api/customer-refunds/{id}/approve` → 200 → `POST .../complete` → 200.
  Rejecting an already-completed refund → 409.

## 6. Expected error shapes

Every service now returns a consistent-per-service JSON error envelope (timestamp,
status, message, path) for 400/401/403/404/409, and never leaks a stack trace or raw
SQL/constraint text — unexpected exceptions are logged server-side and returned as a
generic message. Missing/invalid token → 401. Valid token, wrong role → 403 (this
required a real fix — see §8). Bad path variable / malformed JSON → 400. Unknown
resource → 404. Conflicting state transition or duplicate → 409.

## 7. Suggested presentation flow (10–12 minutes)

1. Show `docs/architecture.md` diagram + `curl :8761/eureka/apps` — all 7 apps UP.
2. Login as admin through the Gateway → show the JWT, then call `/api/v1/cities`
   without a token (401) and as `customer1` on an admin-only route (403) to prove
   the security layer is real.
3. S1: PATCH an Operations Manager's city, then hit the internal validate-city
   endpoint both ways (valid/invalid) — shows cross-service contract validation.
4. S2: upload a real PDF as a verification document via Swagger's file picker, then
   approve the queue entry — retailer status flips live.
5. S3: add to cart, validate, move an item to wishlist, check membership.
6. S5: create a new vehicle assignment (the deliberately-unassigned pair), then try
   it again to show the 409 conflict guard.
7. S6: release an escrow-held payment into a settlement, then process a refund —
   show the 409 on re-running either.
8. Close with the error-handling story: one wrong-role call (403), one malformed
   body (400), one duplicate action (409) — all with clean JSON, no stack traces.

## 8. Hardest feature per service, and how it was resolved

- **S1 — the silent 401/403 bug.** `AccessDeniedHandlerImpl` was correctly configured
  and correctly computed 403 internally, but `sendError(403)` triggers Spring's
  internal `/error` forward, which re-enters the *same* security filter chain with no
  Authorization header — and since `/error` wasn't `permitAll()`'d, that forward failed
  authentication and silently overwrote the response with 401. Invisible to
  `@WithMockUser`-based unit tests (they don't exercise the real error-dispatch path);
  only found by testing live with real JWTs. Fixed by adding `/error` to `permitAll()`
  in every service's `SecurityConfig` — the same one-line fix, six times.
- **S2 — real multipart storage without breaking the existing versioning workflow.**
  The verification-document model already had `versionNumber`/`isCurrentVersion`
  semantics baked in from an earlier (string-only) implementation; the hard part was
  wiring a real file (validated by both extension and content-type, size-capped) into
  that model without duplicating or corrupting the version chain, plus quietly fixing a
  self-inflicted import collision (`swagger`'s `RequestBody` shadowing Spring's) caught
  by the test suite.
- **S3 — Feign failures degrading gracefully.** Checkout depends on S4/S1 being
  reachable; previously any downstream hiccup surfaced as a raw 500. Wrapped every
  outbound Feign call in a shared helper translating timeouts/unavailability into
  503/504 with a `retryable` flag, verified live by literally taking S4 down mid-demo.
- **S4 — shrinking `TripService` without touching behavior.** The file was ~2x longer
  than its logic warranted from a one-argument-per-line style used nowhere else in the
  codebase, plus four duplicated "fetch via Feign, 404 on miss" blocks. Reformatted and
  extracted a shared lookup helper, then proved equivalence the only way that counts —
  identical test counts (128/128) and identical live responses before/after.
- **S5 — a bug that made vehicle creation *always* fail.** `VehicleServiceImpl`
  checked S2's fleet-owner status against values S2 never actually returns
  (`ACTIVE`/`APPROVED` instead of the real `VERIFIED`/`ACTIVE`), so no vehicle could
  ever be created against a real fleet owner — invisible in unit tests because they
  mocked the Feign response to match the wrong expectation too. Only surfaced by
  running S2 and S5 together and hitting the real internal validation endpoint.
- **S6 — interpreting "Escrow" onto a codebase that has no Escrow entity.** Rather than
  bolt on a new table, mapped the requirement onto the existing
  `PaymentTransaction.escrowStatus` + `Settlement` + `CustomerRefund` state machine,
  which already had the right shape (hold → release/refund) but several silent gaps
  (duplicate payments per order were allowed, `BusinessRuleException` returned 422
  instead of the more correct 409 for state conflicts, Feign failures fell through to
  bare 500s). Closed each gap without renaming or restructuring the existing entities.

## 9. Known, documented, out-of-scope gaps

- `/actuator/health` is `permitAll()`'d in several services' `SecurityConfig` but the
  actuator starter isn't actually on every service's classpath, so it 404s rather than
  returning a health payload — pre-existing, not fixed (out of scope; the fix would be
  a `pom.xml` dependency add per affected service).
- Per-resource-ownership enforcement beyond S1/S3 (e.g. "is this YOUR order") still
  stops at the Gateway's coarse role check for S2/S4/S5/S6, per `architecture.md` §5 —
  unchanged in this pass, flagged as a follow-up.
- S6 entities still have no `@Column(nullable=/length=)` annotations (relies entirely
  on Hibernate defaults) — a real but low-risk gap for an H2/dev-scale demo.
