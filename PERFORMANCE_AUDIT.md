# AroundU — Complete Application Performance Audit

End-to-end performance audit of the AroundU platform: Angular 19 frontend, API Gateway, six Spring
Boot microservices (S1–S6), Feign inter-service calls, and the shared PostgreSQL database. This audit
builds directly on an earlier, narrower performance pass (documented in
`CR-Documentation/CR-CHG0030033-Performance-Optimization.md`, Iterations 1–2) — that work is not
repeated here except where directly relevant; this document is the full-scope follow-up requested
separately, covering areas that prior pass did not reach: admin/ops/LM dashboards, verification queue,
support tickets, notifications, user accounts, the remaining JPA entities (S1/S2/S4/S6), and
multithreading/async/concurrency across all six services.

Every finding is evidence-based (file:line) and labelled exactly one of: **Confirmed issue**,
**Confirmed efficient implementation**, **Potential concern requiring runtime measurement**, **Not
applicable**. No timing, cache-hit, or throughput percentage is claimed anywhere in this document —
the development dataset is tiny (27 orders, 30 products, 5 retailers, 150 notifications, 11 support
tickets, 29 verification-queue entries, 40 audit-log rows), far too small for a timing comparison to
mean anything; the evidence used instead is request/query **counts**, index **existence**, and direct
**code structure**, all of which are meaningful regardless of data volume.

## 1. Application architecture summary relevant to performance

```text
Angular 19 (standalone components, signals) — 88 lazy-loaded routes (loadComponent/loadChildren)
        ↓ HttpClient (2 interceptors: auth, audit — no HTTP-level cache interceptor exists)
API Gateway (Spring Cloud Gateway, WebFlux — reactive because the framework requires it, not a
             custom choice; JWT validated here; role-based route rules; 3s connect / 60s response timeout)
        ↓ (Eureka service discovery, "lb://" load-balanced routes)
S1 platform-territory | S2 partner-verification | S3 commerce-customer
S4 order-logistics    | S5 fleet-operations      | S6 finance-support
        ↓ each: Spring Boot 4.1, Spring Data JPA/Hibernate, HikariCP
                 Feign to the others (3s connect / 30s read, Spring Cloud OpenFeign's default
                 Retryer.NEVER_RETRY — confirmed no custom Retryer bean exists anywhere, so no
                 retry-amplification risk)
        ↓
One shared PostgreSQL database (Commerce_Operations_Control_Tower_db), no per-service DB, no
Flyway/Liquibase — schema is generated by Hibernate's `ddl-auto=update` from `@Table(indexes=...)`
annotations, which is also how every index in this document (and the prior CR) was actually applied.
```

No Redis, no message broker, no `@Async`/thread pool/executor anywhere in application code (see §13).
No charting library exists in the frontend (`grep` for Chart.js/ngx-charts/d3/etc. across the whole
frontend returned zero matches) — every "chart" in the app is a computed signal producing CSS
width/`stroke-dasharray` values from already-fetched data, so lazy-loading-a-chart-library is **Not
applicable** anywhere in this codebase.

## 5. Lazy/eager loading findings

**Frontend:**
- **Confirmed efficient implementation** — Angular routes: 88 `loadComponent`/`loadChildren` call sites
  in `app.routes.ts`, confirmed by the production build output (100+ separate lazy chunk files, e.g.
  `dashboard-component`, `catalogue-component`, `finance-component` each its own chunk). No route
  eagerly bundles a feature it doesn't need.
- **Confirmed efficient implementation** — Location Manager dashboard's per-row `assets`/`reviews`,
  and Verification Queue detail's document blob preview, are both fetched strictly when the user
  expands that specific row/document, not for every row up front.
- **Confirmed issue** — Support staff screen loads all 4 tabs' data on mount rather than on tab-select
  (§3/§18).
- **Not applicable** — no chart library exists to lazy-load.

**Backend JPA:**
- **Confirmed efficient implementation (baseline)** — every entity relationship checked across S1
  (`LocationManager`, `OperationsManager`, `City`, `Zone`), S3 (`CustomerCart`, `CustomerCartItem`,
  `CustomerReview`, `CustomerWishlistItem`), and S4 (`Trip`, `LogisticsBookingDetail`) declares
  `fetch = FetchType.LAZY` **explicitly** — the codebase does not rely on JPA's default eager fetch for
  `@ManyToOne`/`@OneToOne`. S2 and S6's cross-entity references are plain scalar UUID/Long columns with
  no JPA relationship at all (by design, documented in-code as "never a JPA relationship to another
  service's table" since these services share one database but must not entity-couple across service
  boundaries) — lazy/eager is **Not applicable** to those.
- **Confirmed efficient implementation** — S3's cart (`findWithCartAndProductByCartCustomerId`,
  join-fetching cart+product) and product listing (`fetchCategory()` join-fetch) already avoid N+1 via
  explicit fetch joins, confirmed in the prior audit round and re-confirmed here.
- **Confirmed issue** — the LAZY declaration is respected at the entity level but several **list**
  endpoints still touch those LAZY associations in a per-row loop with no fetch join at the query
  level, producing N+1 SQL despite "correct" LAZY entity mapping. This is the single most common
  backend pattern found this round — see §8/§10 for the specific methods.

## 7. Another-PC / browser-refresh cache behavior

**Same browser/navigation.** Every `TtlCache` and the `myRetailer`/`myFleetOwner` signals live in
`providedIn: 'root'` singleton services, so navigating between routes within the same tab reuses the
same instance and its cached value — confirmed by reading the DI scope of every cache listed in §6.

**Browser refresh.** A full page reload destroys the entire Angular application and recreates every
service from scratch, so every cache in §6 resets to empty — there is no persistence layer (no
`localStorage`/`sessionStorage`/IndexedDB backing any of them). This is expected, correct behaviour,
not a defect.

**Another PC / another browser.** Because every cache is pure in-memory JavaScript state private to one
browser tab's running application, a session on a different computer (or a different browser on the
same computer) starts with completely empty caches and independently fetches its own data, authenticated
by its own JWT. Nothing here depends on a machine-specific path, a hardcoded URL, or state left behind
by another machine — confirmed by inspecting every cache's key/scope in §6, none of which reference
anything machine- or browser-specific.

**Multi-user safety.** The account-scoped caches (addresses, retailer/fleet-owner "my profile") are
keyed by the account id embedded in the request itself, resolved server-side from the caller's own JWT
— one user's session can never populate or read another user's cache entry, because each browser tab
has its own completely separate in-memory `Map`/`signal` instance to begin with (there is no shared
storage of any kind to leak across).

No server-side/shared cache (Redis or otherwise) exists anywhere in this codebase, confirmed by
`grep`-ing for Redis/EhCache/Caffeine/`@Cacheable` across all six services — none were found. Nothing in
this document claims otherwise.

## 8. Backend/API/service findings

**Confirmed efficient implementation (already correct, re-confirmed this round):**
- S3's product listing (`Specification`+`Pageable`+`JOIN FETCH` category), cart (`join fetch`), review
  and wishlist services (batched retailer resolution, `IN`-query membership checks) — no changes needed.
- S2's `LocationDashboardService` — a page of partners costs a fixed number of calls (one accounts
  batch, one rating batch, one queue query) regardless of page size — the reference pattern this whole
  codebase should follow for any new paginated staff screen.
- S4's `deductStock`/`OrderService` core order-creation path — already fixed for the payment/weight
  consistency issues in an earlier CR; no new order-path issue found this round.
- S6's `NotificationServiceImpl`/`AuditLogServiceImpl` write paths — a single local insert plus a
  best-effort (audit) or required (notification) identity check; cheap regardless of scale.
- S5's Feign-exception handling (`GlobalExceptionHandler.handleFeign`) — never forwards a raw
  downstream error, already fixed in an earlier round.

**Confirmed issue (new this round):**

1. `S1-platform-territory/.../repository/LocationManagerRepository.search()` has no `join fetch`;
   `LocationManagerServiceImpl.toDto()` then dereferences 6 different LAZY associations
   (`userAccount`, `zone`, `zone.city`, `zone.city.state`, `operationsManager`,
   `operationsManager.userAccount`) per row — up to 6 extra SQL queries per row on the Location
   Managers list. **Not fixed this round** (a join-fetch rewrite risks subtly changing which rows a
   paginated query returns if not done carefully — see §18 for the recommended approach).
2. `S1-platform-territory/.../OperationsManagerService.toResponse()` — same pattern, 2 LAZY
   associations per row (`userAccount`, `city`), no fetch join on the underlying paged query. **Not
   fixed this round**, same reasoning.
3. `S4-order-logistics/.../TripService.toDto()` — a lazy `Order` load plus **3 sequential Feign calls**
   per row (driver, vehicle, fleet-owner summaries), self-documented in the code's own comment as
   "intentionally not fixed with a batch endpoint here." **Not touched this round** — overriding an
   explicit prior author decision without a batch endpoint already available is out of this audit's
   safe-fix scope (see §18).
4. `S4-order-logistics/.../LogisticsBookingDetailService.getAll()` — `findAll()` (unpaginated) then
   `booking.getOrder().getDeliveryCharge()` per row (a lazy load, no fetch join). **Not fixed this
   round** — see §18.
5. **S6 — every list endpoint across all five list-serving entities is a plain unpaginated
   `List`/`findAll()`**: `GET /api/audit-logs`, `GET /api/notifications`/`/mine`,
   `GET /api/payment-transactions`, `GET /api/settlements`, `GET /api/support-tickets`/`/mine`/
   `/escalated-to-me`. None of these entities has any JPA relationship (all cross-references are plain
   scalar columns), so there is no N+1 *inside* the mapping itself — the confirmed issue is purely
   unbounded result size. **Not fixed this round** — pagination here needs matching frontend changes
   across 3 components (`finance.component.ts`, `support.component.ts`, the notification bell), which
   is a larger, coordinated change than this pass's scope; see §18.
6. `S6-finance-support/.../SettlementServiceImpl.resolvePayeeNames()` (lines ~39, 51-59) loops over
   every **distinct** payee in the (unpaginated) settlement result set and calls a Feign lookup for
   each, memoized with `computeIfAbsent` so a repeated payee costs nothing extra — but the loop itself
   is still sized by however many distinct retailers/fleet-owners have ever been settled, growing
   unboundedly with the settlement table. **Not fixed this round** (fixing it properly requires either
   paginating settlements first, per finding 5, or adding a batch payee-name lookup to S2 — a
   cross-service API change).

## 9. Feign/inter-service/gateway findings

- **Confirmed efficient implementation** — Feign timeouts (3s connect / 30s read, set identically
  across all six services) and gateway timeouts (3s connect / 60s response) were already tuned in an
  earlier round and remain in place, confirmed by re-reading `application.properties`/`application.yml`
  fresh this round.
- **Confirmed efficient implementation** — no custom `Retryer` bean exists anywhere (`grep` for
  `Retryer` across S1–S4 returned nothing), so Spring Cloud OpenFeign's own default,
  `Retryer.NEVER_RETRY`, applies — a slow/failing downstream call is never retried, so there is no
  retry-amplification risk anywhere in this platform.
- **Confirmed efficient implementation** — S2's verification/document notification sends
  (`AfterCommit.run(...)`, `VerificationQueueServiceImpl.java:598`,
  `VerificationDocumentServiceImpl.java:344-354`) defer the Feign call until **after** the enclosing DB
  transaction commits, via a registered `TransactionSynchronization.afterCommit()` callback — this
  releases the database connection before making the blocking network call, unlike the pattern below.
- **Confirmed issue (Potential concern requiring runtime measurement for exact magnitude)** — S4's
  `OrderService.notifyFleetOwnerBestEffort`/`notifyRetailerBestEffort`/`notifyCustomerBestEffort`
  (`OrderService.java:417-428, 786-807`) are synchronous Feign calls made from **inside** the same
  `@Transactional` method that changed the order's status — the database connection stays checked out
  of the pool for the duration of that external HTTP round-trip. Under load, this is a genuine
  connection-pool-pressure risk (not just added latency), unlike S2's already-fixed pattern. **Not
  fixed this round** — restructuring S4's transaction boundaries to match S2's `AfterCommit` pattern is
  a correctness-sensitive change to order-status-change code that deserves its own focused pass rather
  than being bundled into a broad audit; see §18.
- **Confirmed issue (minor, latency-only)** — S1's `AuditRecorder.record(...)` makes a synchronous
  Feign call to S6 inline with the triggering staff action, wrapped in try/catch so a failure never
  blocks the action, but still adds a network hop to the request's response time. Small in absolute
  terms (S6's side is one cheap local insert) — flagged as a measurement candidate, not a proven
  problem.
- **Confirmed efficient implementation** — gateway JWT validation writes only a status code on
  auth/role failure (no body assembled, nothing to leak, minimal work per rejected request) — already
  confirmed correct in the prior UX/message audit round.

## 13. Async/multithreading findings

**Confirmed efficient implementation — no `@Async`/thread pool/executor exists anywhere in application
code.** A repository-wide search across all 8 modules (S1–S6, gateway, eureka) for `@Async`,
`CompletableFuture`, `ExecutorService`, `ThreadPoolTaskExecutor`, custom `Executor` beans,
`Executors.new*`, and `.parallelStream()` returned zero matches. No `server.tomcat.threads.*` is
configured anywhere — every service runs on Spring Boot's default embedded-Tomcat pool. WebFlux/
reactive types exist **only** in `api-gateway`, which is a Spring Cloud Gateway application (reactive by
framework requirement, not a custom design choice).

**The only real concurrency constructs found:**

1. **Two `@Scheduled` jobs**, both **confirmed efficient implementations**: S4's
   `RetailerResponseTimeoutJob` (every 60s, `fixedDelay` — deliberately not `fixedRate` so a slow
   notification call can't cause overlapping runs — its own comment states this explicitly) and S6's
   `SupportTicketSlaScheduler`/`TicketClusterScheduler` (every 15/30 min, each wraps its entire sweep
   body in try/catch so no exception vanishes silently). Both run on Spring's default single-threaded
   scheduler (inherently bounded), and neither offloads anything transactionally-critical to a race
   against a concurrent HTTP request — they are the authoritative periodic mutator of their own state,
   not a shortcut around a synchronous flow.
2. **Dev-only background-thread `DataSeeder`s** (S2–S6, not S1): a plain `new Thread(...)`, named
   exactly `"seed-s2"`…`"seed-s6"` (matching the `[seed-sN]` log-thread-name pattern that prompted this
   check), started as a daemon thread so it never blocks JVM shutdown. **Confirmed efficient
   implementation given the stated dev-only scope**: each service is genuinely reachable (and
   Eureka-routable) before its own seed data finishes writing — a real but narrow race — but every seed
   row is looked up idempotently by business key first, cross-service dependencies are resolved via a
   bounded (7-minute-timeout) polling wait rather than a fixed start order, and the whole mechanism is
   gated by an `app.seed.enabled` flag meant to be off outside development. Not a production-traffic
   concern.
3. **Notification/audit dispatch is synchronous everywhere** (no queue, no async hand-off) — see §9 for
   the one confirmed resource-risk pattern (S4's in-transaction Feign calls) and the one already-fixed
   pattern (S2's `AfterCommit`).

**Confirmed efficient implementation — order creation, payment confirmation, stock deduction, tax
calculation, verification decisions, and driver/vehicle assignment all run synchronously on the request
thread inside their own `@Transactional` method.** None of these correctness-critical flows is
offloaded to a background thread anywhere in the codebase — there is no async-related correctness race
to report for any of them.

## 18. Remaining limitations (confirmed issues, not fixed this round, with why and what the fix would look like)

- **S1 `LocationManagerRepository.search()`/`OperationsManagerService` list N+1** — fixing this
  correctly means adding `JOIN FETCH` (or an `@EntityGraph`) to the *paginated* query without changing
  which rows a given page returns (fetch-joining a to-many side can silently affect `Page` counts if
  done carelessly; both associations here are to-one, so it's safe in principle, but the query is used
  by more than one caller and deserves its own focused change + test pass, not a bundled edit inside a
  broad audit).
- **S4 `TripService.toDto()`'s 3-Feign-call-per-row N+1** — the original author explicitly documented
  this as "intentionally not fixed... a batch endpoint here" was out of scope at the time. Building that
  batch endpoint (driver/vehicle/fleet-owner summaries by a list of ids, on S5/S2) is itself the correct
  fix, but it's a cross-service API addition, not a same-service tweak — left for a dedicated pass.
- **S4 `LogisticsBookingDetailService.getAll()`** — same lazy-`Order`-per-row pattern; smaller blast
  radius than `TripService` (this endpoint has fewer confirmed callers) but not touched this round for
  the same "don't bundle a query rewrite into a broad audit" reasoning.
- **S6: every list endpoint (audit logs, notifications, payment transactions, settlements, support
  tickets) is unpaginated** — the backend fix (adding `Pageable` to 5 repositories + 5 controller
  methods) is mechanical, but it requires matching frontend changes in `finance.component.ts`,
  `support.component.ts`, and the notification bell to actually request/render pages instead of a full
  list — a coordinated, multi-file change better done as its own tracked piece of work than folded into
  this audit.
- **S6 `SettlementServiceImpl`'s Feign-loop over distinct payees** — depends on the settlement-pagination
  fix above (paginating settlements first shrinks the loop to one page's worth of distinct payees
  automatically) or a new batch-payee-name endpoint on S2 — either is a real design decision, not a
  same-file tweak.
- **S4's in-transaction notification Feign calls** (§9) — the correct fix is S2's already-proven
  `AfterCommit` pattern, but moving S4's notification calls out of the transaction touches
  order-status-change code, which this audit's own instructions explicitly call out as needing extra
  care ("Do not weaken... order logic... payment logic... data consistency") — deliberately left for a
  focused, order-flow-specific change with its own regression testing, not bundled here.
- **Verification queue's unpaginated list + first-load per-subject N+1** — pagination is a backend
  change (`VerificationQueueService` + repository), and the N+1 would need either a batch
  "resolve these subject ids" endpoint or accepting the current dedup-for-repeats mitigation as
  sufficient at this platform's current queue sizes (29 rows in the live dev data).
- **Support staff screen loading all 4 tabs up front** — a small, mechanical frontend fix (move each
  tab's load into its `@if (activeTab() === ...)` branch instead of `ngOnInit`), not implemented this
  round purely due to the sheer number of other confirmed items competing for the same safe-change
  budget in this pass; flagged as the easiest remaining win.
- **Admin Accounts screen's fetch-all + client-side filtering** — now cached for 60s (§14) but still
  transfers the full table on a cache miss; a real fix needs server-side search/filter/pagination on
  `GET /api/user-accounts`, mirroring the pattern S2's `LocationDashboardService` already proves works
  well in this codebase.
